# ActiveTab Navigation

## Purpose

Coordinate navigation planning, browser execution, bounded recovery, and visible destination checks using the native CDP runtime.

## Ownership

`ApplicationRunService` is the shared HTTP/MCP boundary for acquiring the exact target lease and invoking `NavigationEngine`, and for constructing declarative `TestRunner` runs with shared diagnostics and durable run-state binding. Entry adapters own session selection, journals, run tracking, and response projection. `NavigationEngine` owns the navigation state machine and sends effects through `executeAuthorizedAction`. `outcomeVerifier.js` owns pure checks for whether fresh visible navigation evidence matches a requested destination. It does not authorize or dispatch operations.

## Local Contracts

- Every effectful browser operation remains behind the shared authorized executor and current environment/target checks.
- Links that would create another browser target are not followed implicitly. A trusted qualification may explicitly route observed root-frame anchors through same-target navigation; candidate identity, exact destination scope, and lease are checked immediately before dispatch.
- After a dispatched click, a failed post-action observation may be retried once while the target remains attached. If that retry discovers a delayed detach, the trusted CLI or shared HTTP/MCP composition may reconnect only to the original loopback endpoint and exact target ID under the still-current durable lease. It checks the authorized environment origin before and after attach, binds the replacement session to the same lease, and takes fresh evidence before any later dispatch. The browser action is never repeated; if fresh evidence is still unavailable, stop unresolved and return bounded reconciliation diagnostics, including an allowlisted reattachment failure code. Reattachment is supplied only by trusted composition and is not inferred for arbitrary sessions; extension-managed targets use broker recovery.
- Form target labels may be normalized for matching, but exact caller values must resolve from a raw literal or caller input binding and must never pass through token normalization. Shared browser action limits reject oversized values before dispatch.
- Native workflow form capabilities are created only for a declared application and trusted fill/select/toggle/apply-filter operation IDs. Values come only through caller `inputRef` bindings; credential and file controls remain excluded. Toggle is limited to an exact native checkbox; apply-filter is limited to an observed non-submit button and verifies only a visible result transition. Both require scoped operation authorization, and the executor rechecks capability scope against fresh evidence before dispatch.
- Workflow mode always includes the generic observed-link capability and adds profile-supplied capabilities. Generic navigation is explicitly marked `generic_navigation`; application-specific capabilities default to `caller_required` and reach synthesis only when their exact IDs appear in typed `requiredCapabilityIds`. Native fill/select registration comes only from the exact resolved application's `workflow_operations`; it remains subject to caller `inputRef` bindings, policy admission, and the independent typed operation authorizer. Duplicate capability IDs fail synthesis rather than shadowing the generic capability contract.
- Required workflow capabilities may be intermediate steps: each must support an allowed task purpose, while the full validated plan must retain an unconditional trusted postcondition witness for the requested final outcome. Value-bearing capabilities may additionally bind to one exact trusted `requiredInputRef`; synthesis cannot substitute another caller input.
- `workflowCapabilityCatalog.js` validates the trusted capability contracts and returns both a local normalized catalog and a model-safe projection. Trusted resolver, verifier, and executor functions remain only in the local catalog; the projection exposes bounded codes and whether resolution is dynamic, never those functions or additional authority.
- If a task requires registered workflow capabilities, missing synthesis or invalid synthesis stops planning without selecting a deterministic fallback action. Standalone model planning sends only visible, enabled candidates meeting the local relevance threshold; model output must still select from that exact shortlist.
- Page labels are untrusted model evidence. Before standalone navigation planning, any mutation verb in a candidate name or section context excludes that candidate from a navigation proposal, even when prompt-like text precedes the verb; the returned reference must still resolve within the exact submitted shortlist.
- The secondary semantic analyzer may receive bounded region, collection, record-field, and native interaction context only when it matches the exact observation, target, and document generation. Field labels and values reach the provider only under the separate page-label disclosure opt-in. Semantic context remains evidence for candidate mapping; its operation effect is always `unknown`, and it cannot authorize or verify an action. Decision telemetry retains the bounded structure and typed field roles but redacts every page-derived label and value.
- Generic link verification binds to the exact destination in the fresh selected link, checks the same target and document generations, and requires fresh visible destination context for SPA transitions in addition to the expected URL and environment/application identity. It rejects handoff/error states and requires before/after evidence references. A `verified` label without a matching capability, verification code, destination proof, and fresh evidence references never completes a workflow step.
- HTTP and MCP navigation and declarative workflow tasks use `ApplicationRunService`; adapters cannot construct a navigation engine or workflow runner outside the shared service composition. `TestRunner` continues to acquire and enforce its durable run lease for workflow effects.
- Validated API template inputs are passed to local planning as caller-owned `inputBindings` and workflow inputs. The standalone deterministic planner resolves only explicit `inputRef` values; model planning receives no raw bindings, and journals/telemetry must not serialize the bound values.
- The outcome verifier stores only hashes of initial page title/heading labels and evaluates fresh observations against the requested goal and bound environment.
- A fresh HTTP 429 signal suspends the current run for operator handoff. ActiveTab does not automatically retry, rotate identities, or bypass a rate limit; resumption requires fresh evidence after the operator resolves the wait.
- A navigation destination match is not proof that a website-side operation or application task completed; those require the application's declared verification oracle.
- Remote screenshot input requires image support discovered for that model route at startup and the separate privacy opt-in (`ACTIVETAB_MODEL_ALLOW_SCREENSHOTS=1`). If catalog capability is unavailable, an explicit `ACTIVETAB_MODEL_IMAGE_INPUT=1` declaration can serve as a fallback. These settings enable image use but do not require images on every semantic or workflow request; those callers must explicitly request or supply visual evidence. Jev additionally requires `ACTIVETAB_JEV_ALLOW_IMAGES=1`. Images are bound to the exact observation, target, document generation, and viewport and may only help interpret or select identities already present in that observation.
- Screenshot capture follows the active task's explicit image requirement, never Jev's global image capability. Ordinary navigation and authorization observations use the interaction profile and avoid screenshot capture. A visual planner request may use CDP clipping scale to fit Jev's experimental image bounds; telemetry keeps the source viewport, actual JPEG dimensions, pixel-to-viewport transform, and digest, while image bytes stay out of events.
- When deterministic planning returns an unexplained page state, the engine may capture one fresh visual observation if image input is explicitly enabled and ask Jev for bounded page-state/obstruction assessment. For ambiguous candidate ties, `auto` mode may instead send a bounded target-role code with one bound screenshot and batch Jev Noul presence plus Box grounding. A Box may select only from the deterministic candidate shortlist; the engine reobserves and checks the exact candidate, target, document generation, and visible bounds before continuing through normal policy and the authorized executor. Unmapped cross-frame bounds abstain. Visual output remains advisory and cannot authorize an effect, verify an application outcome, or dispatch raw pixel coordinates.
- `npm run pretest:secondary`, `npm run pretest:jev-visual`, and `npm run pretest:multimodal` perform opt-in provider protocol pretests using synthetic evidence and the static fixture image. They do not qualify an application, workflow, or browser target. They never dispatch browser operations and remain separate from unit tests.
- Synthesized workflows may invoke qualified, exact-scope extraction capabilities supplied by the capability registry, or a run-local one-shot table read compiled from the current retained DOMSnapshot. The run-local path is available only for exact requested fields that pass trusted classification, read, and release policy; it revalidates the target, principal, document generation, full route, and source structure immediately before extraction, never registers or persists a reusable capability, and reports `observed_partial`. It cannot satisfy a caller request that asserts all/every/complete coverage. Registered pagination supports visible same-path `rel=next` links, exact-label next links/buttons, monotonic page-number query parameters, and verified virtualized-list scrolling. Page advances are freshly resolved and dispatched through the authorized executor under the live target lease; collection requires nonduplicate record or cursor progress, and terminal proof requires a nonempty final page. Extraction output must pass field-release policy and independent schema, provenance, uniqueness, and completeness verification before a complete registered workflow can finish. Extracted output values stay out of model input and task journals; separately projected visible page evidence remains governed by page-content consent. MCP stores partial registered-collection checkpoints separately in owner-only result artifacts, strips query strings from source routes, and rechecks target, environment, principal, typed intent, release policy, and extraction verification before resume or artifact replay. Unresolved operations are never checkpointed; virtualized scroll and same-URL button transitions abstain from checkpointing when their next cursor cannot be reconstructed safely.
- A current-page atomic read may execute as a local one-step workflow when fresh observation produces exactly one trusted ephemeral `observed_partial` read capability for the caller's exact requested fields and the task intent requires only that capability. The planner records a deterministic route and uses the same extraction policy and output verifier; it does not invoke GLM or Jev. Composite, transformed, ambiguous, incomplete-scope, or otherwise unresolved requests retain the normal synthesis or abstention path.
- Workflow diagnostics expose per-step statuses and bounded lowercase reason codes for extraction failures. They must not include extracted values, page text, provider messages, or credentials; successful steps omit failure codes.
- Workflow-provider usage is normalized from OpenAI-compatible token fields to the bounded telemetry usage contract before it is appended; preserve input, output, total, cached-input token counts, and cost when supplied.
- Workflow synthesis failure telemetry retains generated request UUID, bounded latency, fixed transport cause code, and validated HTTP status when available, allowing local inference-proxy correlation without storing provider messages, endpoint values, or credentials.
- Keep workflow synthesis, Jev review, per-run inference budgets, browser freshness, and recovery limits unchanged when extracting navigation responsibilities.
- `createNavigationRunContext()` derives one run's counters, failed-target exclusions, scroll convergence map, target/environment binding, journal identity, and latest observation from the canonical task state. The context does not dispatch browser actions or change which service owns authorization.
- `NavigationEngine.run()` accepts caller-owned resume state, cancellation, workflow intent/inputs, and input bindings; internal execution state and inference-budget bypasses cannot be supplied through private options. Each non-pre-aborted public run enters the configured per-run inference budget exactly once.
- `ActionAttemptCoordinator` persists pending action metadata before dispatch and settles it into canonical task state afterward. It cannot dispatch browser actions; `NavigationEngine` retains planning, policy admission, and authorized execution.
- `ReplayCoordinator` validates stored workflow signatures and replay preconditions against fresh observations; `NavigationEngine` remains responsible for policy admission and authorized dispatch. `RecoveryCoordinator` performs bounded post-action observation retry and exact-target reattachment only; it never repeats the dispatched action.
- Workflow and standalone automatic routing preserve typed task `cardinality` values `atomic`, `compound`, or `unknown`; task wording never grants an effect. In `auto`, explicit read requests, caller-typed workflow intents, and multi-action requests enter the workflow planner against the current trusted capability set. Missing required capabilities, unavailable synthesis, or an incomplete plan abstains before a partial action. Ordinary single-step navigation retains deterministic and semantic routing. Execution still passes the normal policy/lease gate and visible/independent verification.
- Workflow mode accepts an ordinary navigation request without internal capability IDs only when it maps to the existing trusted `follow_observed_link` contract (`navigate` → `route_changed`). Its cardinality remains `unknown`, so a failed synthesis cannot fall back to one partial action. With `ACTIVETAB_MODEL_ALLOW_GOAL_TEXT=1`, unresolved read goals may bind to one trusted current-page read capability, or to a deferred observed-read capability for a composite request whose output fields map to supported semantic roles. Composite reads remain `unknown` cardinality; the read result is required as the task outcome, and generic navigation is exposed only when the request names navigation or control work. One explicit `Search for <phrase> and return/list/show/extract/read/collect/retrieve <fields>` shape may compose an exactly bound caller query, one uniquely observed same-origin GET search form, and an ephemeral `observed_partial` read. It is available only when the field and submitter are unique, the form targets the same browsing context, search results for the exact query are verified, and all steps pass through the normal target lease and authorized executor. The query value stays in the local input binding and capability closure, not capability metadata or input-reference projections; if goal-text egress is enabled, the raw goal follows that separate consent. Extraction fields are derived from the result clause, not the query. Filtering, sorting, ranking, comparison, and summary requests remain unresolved until a trusted operation can establish those results; plain extraction cannot satisfy them. Mutation, submission, mixed-effect requests, unrelated read capabilities, and tied matches are excluded. Ambiguous or unmatched goals abstain. Goal-text egress is separate from page-evidence and screenshot consent. A supplied caller-typed intent is accepted only when it retains the exact trusted capability set required by this route.
- An atomic current-page read bound to exactly one policy-approved ephemeral observed-read capability is compiled locally into one extraction step. This is a call-cost optimization over the existing evidence and capability contracts; it cannot add fields, broaden permissions, change `observed_partial`, or satisfy composite/read-transformation requests.
- `classifyTaskRequest()` performs a local, non-authorizing first-pass task-shape classification before the initial observation. Explicit read-only requests with no requested navigation or control interaction select the `structural` profile: fresh semantic compilation runs without candidate derivation. Mixed, typed, unknown, or control-oriented tasks select `interaction`. Final task-intent resolution still happens after observation, when the engine can bind the goal to the current trusted capability set; the classifier never returns the raw goal or grants capabilities.
- In default `auto` mode, explicit read/extract/collect/retrieve/summarize/compare/scrape goals and output requests such as “list the names” or “return the prices” enter the guarded workflow path so a single navigation cannot stand in for a requested data result. A current-page read binds to one uniquely observed table or record group under the trusted field policy. A composite read may resolve its source at the later extraction step, but only for the fixed requested semantic fields and against that step's exact fresh observation. Public reads use exact-origin run-local grants bound to the approving principal, target, source, requested fields, limits, and expiry; profile-bound reads use the profile policy. Results remain `observed_partial`, and completeness requests require a matching qualified capability. No raw goal text is sent unless `ACTIVETAB_MODEL_ALLOW_GOAL_TEXT=1`; page evidence sent for workflow synthesis remains subject to page-content consent. If no unique authorized source or no usable synthesis route exists, the run abstains without browser mutation. MCP may resume a registered paginated read from its protected released-output checkpoint after revalidating its scope and policy; the redacted task journal still contains no output rows or cursor URL.
- If workflow synthesis fails, only a uniquely resolved, high-confidence, non-submitting atomic click or scroll may use its already observed deterministic plan. Compound and unknown tasks stop without selecting a partial fallback action.
- `workflowPlanValidator.js` owns deterministic, provider-independent validation and freezing of typed workflow graphs. The synthesizer owns provider invocation and composing the validated plan; extraction must preserve every target, input, capability, dependency, and postcondition-witness check.
- Dense workflow observations pass the caller goal only to local CDP candidate ranking and the bounded synthesizer. The raw goal is not retained or sent by observation. Interaction evidence exposes the evidence-linked semantic-page v3 model; synthesis uses its page-shape classification, native interaction mechanics, labeled semantic fields, region, form, collection, row, and control references. Field roles and labels retain observed, inferred, unknown, or redacted status, and values retain evidence references. Native mechanics describe browser semantics only; application operation meaning and effect remain unknown. Headed-table row text is included only in the bounded task-relevant projection and only under existing page-content egress consent. The observer reports actual page, returned, and task-scope candidate counts. When an interaction task scope exceeds the initial 200-candidate observation but is at most 384, workflow planning may take one bounded re-observation with that larger limit. Whole-page coverage remains separate from task-scope coverage; synthesis may proceed only when the exact task scope and its competing controls fit the observation and model projection bounds.
- When semantic fields identify one or more best-matching repeated records, workflow synthesis scopes record-level controls to those records, keeps controls bound to each matching record, and retains collection-level controls. Equally matching records remain together as competing candidates; unrelated records in the same collection do not get reintroduced just because they share a collection reference. If no record-level match exists, existing region, form, collection, and lexical scoping applies.
- A page-scoped observation may truthfully report partial page coverage. Synthesis still refuses candidate actions when the interaction candidate scope is incomplete. The only exception is an explicitly supplied atomic task intent whose required capabilities are all trusted, exact, read-only extraction contracts; in that case the model receives only those required extraction capabilities, with generic navigation removed. Compound/unknown tasks, natural-language inferred intents, and any task requiring observed controls remain blocked until interaction coverage is complete.
- The local `Search for <exact phrase>` primitive and the composed search/read workflow may enter text only through the one-run search authorizer. Besides native search inputs, they accept an observer-marked `input[type=text][name=q]` only when the fresh observation binds that visible field to a same-origin GET form targeting the same browsing context. The selected submitter's effective method, action origin, target, and form identity are revalidated before submission, including per-button overrides. The exact bound value stays out of telemetry and task journals; raw goal egress follows `ACTIVETAB_MODEL_ALLOW_GOAL_TEXT`.
- For synthesized plans, record the selected secondary route before inference and call Jev only for multi-step or consequential plans, or when a permitted bound screenshot makes its review useful. Jev receives the bounded dependency graph, branch conditions, and trusted capability purpose/precondition/postcondition codes. Review bindings cover the exact plan, typed task contract, capability catalog, observation, target, document generation, and review-policy version.
- Standalone `auto` navigation sends explicit reads, caller-typed workflows, and multi-action requests through the guarded workflow planner; the planner must resolve them against trusted capabilities and cannot fall back to one partial action. Other navigation resolves fresh DOM/AX evidence locally first, uses Jev for an unclear page state or permitted visual candidate grounding only when image permission and a bound screenshot are available, and sends unresolved single-step candidate selection to the configured secondary planner. That planner receives a bounded semantic-page projection scoped to eligible candidates, preserving evidence-linked region, form, collection, and control relationships plus separate page/task-scope coverage. Operation meanings and effects remain unknown, and collection counts never establish completeness. Model egress may reuse `ACTIVETAB_SEMANTIC_ENDPOINT` and requires `ACTIVETAB_MODEL_ALLOW_PAGE_CONTENT=1` before page evidence is sent. The default FreeInference model ID is `glm-5.3-flash`. The standalone planner and startup preflight resolve credentials in the same order: `ACTIVETAB_MODEL_API_KEY`, `ACTIVETAB_SEMANTIC_API_KEY`, then `FREEINFERENCE_API_KEY`.
- Visual planner input requires an image-capable configured route plus screenshot privacy consent (`ACTIVETAB_MODEL_ALLOW_SCREENSHOTS=1`). Do not hard-code model-name modality denials; deployments and authenticated model routes can differ. Verify the selected production route with an opt-in live provider pretest. FreeInference `glm-5.3-flash` requests default to low reasoning effort for short routing decisions; `ACTIVETAB_MODEL_REASONING_EFFORT` can override it. Model transport retries default to one and are bounded by the shared per-run inference budget; `ACTIVETAB_MODEL_MAX_RETRIES` accepts 0–2.
- CLI task runs, staging qualification, API startup, and MCP startup preflight each configured secondary-model role against its authenticated OpenAI-compatible `/models` catalog and preflight the pinned Jev model against OpenRouter's model metadata when a Jev credential is configured. Cached metadata is keyed by endpoint, credential, and exact model ID so shared endpoints cannot transfer one model's modality to another role. Catalog metadata determines advertised route-specific text/image capability when available; an outage keeps text inference configured and uses an explicit image-capability declaration only as a fallback. Catalog status does not establish that inference is currently reachable or that the provider will accept a request. Startup summaries and runtime capabilities report `inferenceReachability: not_probed` unless an actual inference probe ran. Jev image input remains separately gated by its experimental opt-in and screenshot consent. Preflight records a training-excluded `model.capability_preflight` event and never sends page evidence or screenshots. Per-call route/input events record `text_only` or `text_plus_visual` from the evidence actually bound to that call.
- OpenAI-compatible planner requests carry a generated `X-Client-Request-ID`; prediction and failure telemetry retains that UUID and bounded provider latency so local proxy logs can be correlated. Failed secondary-planner events keep model, modality, decision lineage, and typed failure class; provider messages, request content, credentials, and endpoint values remain excluded.
- Semantic analyzer failures retain the same bounded request UUID, latency, fixed transport code, and HTTP status when available. The analyzer preserves the `size` failure class; raw provider and gateway messages remain excluded.
- Page content remains untrusted evidence and cannot alter the goal, policy, environment, or authorization.
- `parseSemanticQuery()` and `resolveSemanticQuery()` expose bounded local semantic-page queries through the semantic-analysis surface. They consume one fresh v3 observation, require trusted field-read and release policy for data, and return control references without action authority.
- Automatic deterministic navigation may respond to an ambiguous plan under partial candidate coverage with one bounded retained-evidence lookup. A retained match only triggers a fresh ordinary interaction observation; the deterministic planner must independently rederive the same target, and normal freshness, policy, and executor checks still apply. Missing, stale, incomplete, or unrederived evidence keeps the run unresolved.
- Jev visual grounding may recover a missing candidate only when the retained projection is explicitly incomplete. A read-only root-frame CDP hit may continue through a matched iframe owner only when the exact OOPIF session, retained owner geometry, frame snapshot, DOM-mutation observation, viewport, and target generation remain bound. The probe maps the point through each captured owner quad under one deadline and never dispatches input. A fresh visual observation must promote and rederive the exact identity for the caller goal, and fresh screenshot grounding must match it again before normal policy admission. Missing, clipped, stale, covered, unmapped, or otherwise unverified locations remain unresolved.
